# 部署、测试与发布

## 0. 环境准备：全局安装 DSH

执行本文档任何安装命令之前，先确认 Node 已安装，再安装全局 DSH。版本要求：**不低于 `0.1.1-rc.1`**（插件 `package.json` 的 `dsh` 引擎要求为 `>=0.1.1-rc.1`）。

```powershell
node -v
npm install -g @deepseek-ai/dsh@0.1.1-rc.2
dsh --version
```

`dsh --version` 输出不低于 `0.1.1-rc.1` 即可继续第 1 节。

## 1. 安装矩阵

| 设备角色 | 必装插件 | 不应安装 |
|---|---|---|
| 普通员工端 | `kaiwu-praxis` + 三个锁定配套插件 | `kaiwu-praxis-enterprise` |
| 专用企业管理端 | `kaiwu-praxis-enterprise` | 员工端及其 preset 可不装 |
| 兼任管理与员工的电脑 | 两个插件分别安装，但建议使用不同 profile/`DSH_HOME` | 不要共用测试身份数据 |

员工端三个配套插件当前锁定为：

```text
@nanmicoder/dsh-agent-teams 0.1.14
@vectorize-io/hindsight-coding-agents 0.4.3
dsh-better-sidebar 0.17.1
```

## 2. 从 GitHub 安装

员工端：

```powershell
dsh plugin --profile <employee-profile> add git+https://github.com/viccao-yue/kaiwu-praxis.git
dsh plugin --profile <employee-profile> add @nanmicoder/dsh-agent-teams@0.1.14
dsh plugin --profile <employee-profile> add @vectorize-io/hindsight-coding-agents@0.4.3
dsh plugin --profile <employee-profile> add dsh-better-sidebar@0.17.1
dsh plugin --profile <employee-profile> add "@deepseek-ai/dsh-web-app@0.1.1-rc.2"
```

以上命令安装已发布的 `v0.5.1`，包含重复扩展名修复。

安装过程中（pnpm 供应链保护）如果遇到：

```text
Error: ERR_PNPM_IGNORED_BUILDS
```

执行：

```powershell
pnpm approve-builds --all -C "$env:USERPROFILE\.dsh\profiles\kaiwu-employee"
dsh plugin --profile <enterprise-profile> add "@deepseek-ai/dsh-web-app@0.1.1-rc.2"
```

放行后重跑同一条安装命令即可。

企业端：

```powershell
dsh plugin --profile <enterprise-profile> add git+https://github.com/viccao-yue/kaiwu-praxis-enterprise.git
```

员工端和企业端各自独立启动（可分属不同电脑；同机部署时建议用不同 profile）：

```powershell
# 员工端：浏览器打开 http://127.0.0.1:3081
dsh web --profile <employee-profile> --port 3081

# 企业端：管理页面 http://127.0.0.1:3082，中枢 API 默认 127.0.0.1:3099
dsh web --profile <enterprise-profile> --port 3082
```

公司内网中央部署企业端时，先设置环境变量（监听地址、管理员令牌、企业名称）再启动，中枢会同时监听内网地址与 `127.0.0.1`：

```powershell
$env:KAIWU_ENTERPRISE_HUB_HOST = '<企业中枢的内网或VPN地址>'
$env:KAIWU_ENTERPRISE_LOCAL_HOST = '127.0.0.1'
$env:KAIWU_ENTERPRISE_HUB_PORT = '3099'
$env:KAIWU_ENTERPRISE_ADMIN_TOKEN = '<高强度随机令牌>'
$env:KAIWU_ENTERPRISE_NAME = '<企业名称>'
dsh web --profile <enterprise-profile> --port 3082
```

员工端安装完成后，在「员工设置 → 企业连接」填写 `http://<企业中枢内网地址>:3099` 和企业管理端生成的注册码。员工端自身端口只供本机浏览器使用，无需对网络开放。

## 4. 重新打包的正确顺序

正式发布时不要把仓库文件手工覆盖进旧包后直接宣布新版本。推荐流程是：

1. 员工端代码已提交并推送，确定不可变 commit/tag。
2. 从空白便携工作目录安装该 tag，以及三个锁定配套插件。
3. 清理运行时产生的 settings、preset 用户修改、企业身份和会话。
4. 检查包内 `package.json`/lockfile 与实际安装代码一致。
5. 使用 7-Zip 生成 ZIP、内部 7z 和 SFX EXE。
6. 对 ZIP、7z、EXE 分别执行完整性测试。
7. 解压到新目录，使用包内 Node/DSH 实际启动。
8. 浏览器检查 7 名员工、员工设置、企业连接和控制台。
9. 记录大小、SHA-256、源 commit、插件版本和截图。
10. 将最终产物放入带日期/版本的只读交付目录，不覆盖旧批次。

`v0.5.1` 交付包是在 GitHub 标签创建前以本地离线 tarball构建，并对包内源码、ZIP、EXE 解包内容进行了哈希同源校验。源码现已发布为 `v0.5.1`；仓库迁移前仍建议从该标签补做一次 GitHub 空白安装。若重新构建交付包，必须重新记录所有哈希。

SFX 配置的核心约定：

```text
Title="kaiwu-praxis 开物 Praxis 安装"
RunProgram="kaiwu-praxis-portable\start.bat"
```

`start.bat` 必须从自身目录解析 `home`、`runtime\node` 和 DSH 入口，不得依赖全局 Node 或全局 DSH。

## 5. 自动化测试入口

员工端现有测试脚本位于 `scripts/`。旧配置曾忽略整个目录，本次交接已取消该忽略规则；提交交接材料时应一并评审并纳入需要保留的脚本。脚本中的 `cross-device-admin-token` 是隔离测试固定值，不是生产凭据。重要脚本：

| 脚本 | 覆盖范围 |
|---|---|
| `verify.mjs` | preset 与基础结构检查 |
| `test-admin.mjs` | 已启动员工端页面上的员工设置浏览器验收 |
| `test-capabilities.mjs` | 已启动员工端页面上的能力新增、修改、启停和物化验收 |
| `test-capability-tombstone.mjs` | 官方能力删除标记与恢复 |
| `test-tool-policy.mjs` | 工具启停策略 |
| `test-watermark.mjs` | 水印核心 |
| `test-classify.mjs` | 文件分类核心 |
| `test-enterprise-endpoints.mjs` | 员工端企业 API 行为 |
| `test-cross-device-round1.mjs` | 单机三实例协议链路 |
| `test-enterprise-guides.mjs` | 两端使用引导 |
| `test-github-clean-install.mjs` | GitHub 空白安装 |
| `test-split-packages.mjs` | 员工端/企业端拆分边界 |
| `test-document-filenames.mjs` | 资料/SOP 文件名扩展名规范化 |
| `capture-cdp.mjs` | 通过 Edge CDP 打开真实页面并保存验收截图 |

`verify.mjs`、工具策略、文件核心和文件名测试可以直接运行。使用 Playwright、固定端口或测试 profile 的脚本属于实机/浏览器辅助入口，必须先启动脚本所声明的环境；不能把 `ERR_CONNECTION_REFUSED` 误判为产品逻辑失败，也不能在环境未启动时宣称这些脚本已通过。

最低静态检查：

```powershell
node --check lib/client.js
node --check lib/index.js
node --check lib/admin.mjs
node --check lib/enterprise-endpoint.mjs
npm pack --dry-run
```

测试脚本可能依赖本机 DSH 路径、端口或企业端相邻仓库。执行前先读脚本参数，不要照抄旧交接中的固定路径。

## 6. 浏览器实测要求

前端变更不能只靠 `node --check` 或接口测试。至少检查：

1. 启动全新 profile；
2. 浏览器打开对应端口；
3. 观察真实页面而不是只信接口；
4. 操作关键按钮、输入框、弹窗和侧边栏；
5. 检查浏览器控制台；
6. 截图保存到对应测试报告目录；
7. 修复后重新从失败步骤开始完整回归。

涉及企业配置时，至少使用两个不同 `DSH_HOME`，确认不是两个页面共享了同一份本地状态。

## 8. 网络测试选择

- 同一公司局域网：直接使用企业中枢的内网 IPv4，最接近当前真实部署。
- 不同地点：使用公司 VPN/零信任网络；第二轮以 Tailscale 验证该模式。
- Tailscale 允许同一账号登录多台设备，不会互相顶号；设备 IP 通常在同一 tailnet 内保持稳定，但仍应以控制台状态为准。
- 员工端只需要访问中枢 `3099`，自身 3080 只供本机浏览器使用，无需对网络开放。
- 终端身份绑定 `DSH_HOME` 中的状态文件，不绑定某个 Wi-Fi/以太网。换网络后只要中枢地址仍可达，无需重新注册。
